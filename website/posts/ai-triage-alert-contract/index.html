Ai Triage Alert Contract

This post turns a cross-repository AI triage design into a practical homelab narrative: keep the proven Grafana → Keep → Holmes path, fix evidence and ownership, and evolve identity, lifecycle, and dependency-aware investigation without overpromising.

Matthew McGovern · September 24, 2026

Draft: docs/planning/aiops_poc_plan.md

Reference: AI triage deep dive — implementation guide. This draft narrows that guide into a bounded proof-of-concept plan for AI-assisted operations triage.

Purpose

Validate whether AI can improve alert triage in a predictable, auditable, and safe way. The POC keeps the proven Grafana to Keep to Holmes path, fixes evidence and ownership, and tests whether AI can reduce triage noise without automatic remediation or overpromising.

Status and intent

Status: draft v0.1
Audience: infrastructure, SRE, platform, and security reviewers
Goal: decide whether to move from shadow AI triage to assisted triage
Non-goal: production self-healing, model training, or replacing on-call judgment

Current baseline

The live path is Grafana to Keep to Holmes. Alert grouping currently uses alert name plus boundary, with resolveOn: never and time-based closure. The tested baseline includes a shorter versioned prompt, a preserved full environment skill, a Holmes wrapper without mandatory narration, resolver safety for suppressed firing alerts, and core/read-only shadow admission and deduplication.

Live:
- Grafana -> Keep -> Holmes baseline
- Alert name + boundary grouping
- resolveOn: never with time-based closure

Tested:
- Shorter versioned prompt; previous text archived
- Full environment skill preserved
- Holmes wrapper without mandatory narration, verified in CI and rollout
- Resolver safety: suppressed firing alerts retained, malformed responses fail closed
- Core and read-only shadow admission/deduplication

POC objectives

1. Prove stable alert identity across source, rule, boundary, affected subjects, and display title.
2. Produce auditable AI triage output with explicit evidence, versions, and tool results.
3. Reduce duplicate investigations for flapping or recurring alerts.
4. Compare AI-assisted triage against the current baseline using frozen cases.
5. Establish safe rollout gates before any automatic dispatch is enabled.

Scope

In scope:
- Grafana alert delivery into Keep
- Keep normalization, eligibility, deduplication, and shadow admission
- HolmesGPT read-only investigation
- Evidence capture for metrics, logs, Kubernetes objects, and selected traces
- Evaluation harness for frozen incident cases
- GitOps rollout and rollback plan

Out of scope:
- Automatic remediation or self-healing
- Production write actions
- Full AIOps platform replacement
- Model training or fine-tuning
- Replacing human on-call judgment

Success criteria

Identity:
- At least 90% of selected alerts have stable source/rule/boundary identity
- Missing identity is recorded as explicit uncertainty, not guessed

Evidence:
- Every AI triage report includes alert identity, evidence links, tool versions, prompt version, and model/toolset hash
- Reports distinguish confirmed evidence from inference

Deduplication:
- No duplicate Holmes runs for the same incident within the POC window
- Flapping alerts coalesce into one pending investigation until material new impact appears

Safety:
- All Holmes tools remain read-only
- Malformed responses fail closed
- Suppressed firing alerts are retained and visible
- No two automatic dispatch paths run at the same time

Evaluation:
- The POC produces a comparison report for at least five frozen cases
- The report includes answer quality, evidence completeness, execution time, tool time, tokens, and false-positive rate

Architecture

Grafana Alerting
  -> Keep
       - normalize alert
       - assign stable identity
       - apply eligibility policy
       - deduplicate and coalesce
  -> Dispatcher
       - shadow mode first
       - live mode only after gate approval
  -> HolmesGPT
       - read-only investigation
       - versioned prompt and skills
  -> Evidence store
       - alert metadata
       - tool output
       - execution report
  -> Review surface
       - dashboard or report
       - human approval for assisted triage

The POC should not change the proven path before the shadow comparison is complete. New components are added as gates around the existing path, not as a replacement for it.

Ownership

Alerting repo:
- Production Grafana rules, labels, eligibility validation

Management repo:
- Keep/Robusta GitOps, encrypted workflows, prompt archives, rendered skills, lifecycle code, experiments

Workspace config:
- Canonical harness-agnostic skills, scoped installation

Image repo:
- CI-built, digest-pinned Holmes derivative, build tests

Planning repo:
- Cross-repository design, not duplicate deployment manifests

Docs:
- Operational docs live where the system is operated
- Image build guide lives with the image repo

Identity and eligibility

Identity:
- Separate stable source/rule/boundary identity, affected subjects, and display titles
- Preserve real cluster, namespace, service, and container labels
- Treat missing identity as explicit uncertainty

Eligibility:
- Policy distinguishes investigate from observe-only
- Known NAS capacity alerts can be observe-only with a recorded reason
- Replace name-specific CEL exclusions only after migration validation
- Opting out of AI does not hide the alert
- Different NAS symptoms can still justify investigation

Lifecycle gate

Current:
- Alert name + boundary
- 12-hour window
- resolveOn: never
- cron closure

Proposed gate:
- Admits initial impact, material new impact, and verified recurrence
- Coalesces pending work
- Requires continuous explicit recovery
- Silence, missing data, and stale samples are not recovery
- A running slot is not freed on timeout; the real execution is reconciled
- Prior successful investigations are seeded before enabling the gate
- The system never runs both automatic dispatch paths at the same time

AI design

Prompt:
- Universal prompt stays concise: scope, evidence, and response rules
- Prompt changes are versioned and archived

Skills:
- Skills describe system locations, label semantics, safe tools, and diagnostic procedures
- Skills do not contain predetermined diagnoses
- A skill per alert is not required
- Preserve the full environment reference and measure changes before replacing it

Model and tooling:
- Keep model and toolset hashes unchanged when testing only the wrapper or prompt
- Record execution time, tool time, tokens, and repeated context
- Do not overinterpret CPU samples

Evidence requirements

Required evidence:
- Alert metadata and stable identity
- Grafana firing/resolved delivery status
- Keep normalization result
- Eligibility decision and reason
- Holmes execution report
- Tool output references
- Prompt, skill, model, and image versions

Evidence quality rules:
- Separate regressions, prompt behavior, tooling constraints, and evidence gaps
- A GitOps overlay regression proves one cause, not all poor answers
- Removing wrapper narration removes a constraint; it does not make the model smarter
- Use known trace paths, such as project to branch to pipeline to failed job, as regression tests
- Record the repair chain: canonical source, scoped installer, publication step, wrapper deployment, pipeline result, Helm readiness, image digest, and absence of unwanted constraints

Dependency-aware investigation

Application YAML:
- Stable service IDs
- Ownership
- Hosting
- Evidence selectors
- Explicit dependencies

Validation:
- Schema, location, freshness checks, and initial inventory still need design and testing
- DNS, NFS, and network causality require an actual link, not co-location or timing alone
- Individual symptoms remain visible
- Run the dependency-aware view alongside the current correlation before making it primary

Evaluation plan

Case set:
- One post-repair run
- Historically good GitLab cases
- Kubernetes cases
- Datasource cases
- Recurring-incident cases
- NAS capacity cases
- Flapping alert cases

Method:
- Freeze inputs where possible
- Run baseline and AI shadow with the same evidence
- Compare answer quality, evidence completeness, execution time, tool time, tokens, and false-positive rate
- Live reruns are not frozen-input A/B tests
- Review post-repair answer comparison, not prompt-only comparison

Safety and guardrails

Runtime safety:
- Read-only Holmes tools only
- Fail closed on malformed responses
- Suppressed firing alerts retained
- No simultaneous automatic dispatch paths
- Running slots are reconciled, not silently freed

Secrets and state:
- Plaintext credentials, private keys, raw model conversations, live incident history, future ledger/WAL/backups are not in Git
- Encrypted secrets, canonical skills, prompt history, and reviewed experiment records are in Git
- Pin the image digest in GitOps
- Official sources are the upstream Helm charts and HolmesGPT

Rollout phases

Phase 0: Baseline
- Inventory current alerts, grouping, and Holmes behavior
- Record versions and evidence gaps

Phase 1: Shadow triage
- Run AI triage without user-visible dispatch
- Validate identity, eligibility, deduplication, and evidence capture

Phase 2: Assisted triage
- Present AI triage to operators with evidence and confidence
- Require human approval before action

Phase 3: Limited automatic dispatch
- Enable only for eligible, low-risk, high-confidence alerts
- Keep observe-only alerts visible
- Continue shadow comparison for new alert classes

Timeline

Week 1:
- Confirm scope, owners, and success criteria
- Complete baseline inventory
- Verify Grafana firing/resolved delivery into Keep

Week 2:
- Implement shadow dispatcher, durable dispatch, and ledger seeding
- Add non-Grafana normalization and ambiguous-request handling
- Add backups and health metrics for admission

Week 3:
- Run frozen case evaluation
- Review missed or noisy cases
- Validate dependency-aware view alongside current correlation

Week 4:
- Cut over through GitOps if gates pass
- Observe 24-48 hours
- Produce decision memo for assisted or automatic triage

Risks and mitigations

Risk: prompt-only changes are mistaken for model improvement
Mitigation: pin model, toolset, prompt, skill, and image versions; compare post-repair runs

Risk: resolved events are missing or delayed
Mitigation: verify Grafana to Keep delivery, including silence, all-clear, late events, and incomplete reads

Risk: dependency grouping creates false causality
Mitigation: require actual links for DNS, NFS, and network causality; keep individual symptoms visible

Risk: AI noise increases operator fatigue
Mitigation: eligibility policy, observe-only classification, deduplication, and 24-48 hour observation window

Risk: runtime state leaks into Git
Mitigation: keep ledger, WAL, backups, raw conversations, and live incident history out of Git

Deliverables

- docs/planning/aiops_poc_plan.md
- POC runbook
- Evaluation harness and frozen case set
- Shadow dispatcher and ledger design
- GitOps rollout and rollback plan
- Decision memo with evidence and next-step recommendation

Open questions

- Which alert classes are eligible for automatic dispatch after the POC?
- What is the minimum evidence required to mark recovery?
- How should prior successful investigations be seeded?
- Should the dependency-aware view remain shadow-only for one additional cycle?
- What cost and token thresholds should trigger review?
