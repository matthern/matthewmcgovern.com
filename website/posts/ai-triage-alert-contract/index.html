Ai Triage Alert Contract

This post turns a cross-repository AI triage design into a practical homelab narrative: keep the proven Grafana → Keep → Holmes path, fix evidence and ownership, and evolve identity, lifecycle, and dependency-aware investigation without overpromising.

Matthew McGovern · September 24, 2026

AI triage: lifecycle, evidence, and ownership

When a homelab starts running AI-assisted incident triage, the tempting answer is to make the system feel smarter by adding more context, more playbooks, or more aggressive automation. The harder, more useful answer is to make the system more honest: preserve the parts that already work, make the evidence auditable, separate identity from noise, and keep durable runtime state out of Git configuration.

That is the goal here. The existing Grafana → Keep → Holmes investigation flow remains the foundation. New alerts should enter through consistent identity and policy. Flapping alerts should not trigger repeated investigations. Symptoms should be correlated through known application dependencies, not guessed relationships. Git-managed YAML is the source of truth for policy and application/dependency definitions, while durable runtime state and incident history remain operational data, not configuration.

What is deployed versus what is still unfinished

The most important part of any deep-dive is knowing what is actually running. As of the 2026-09-23 checkpoint, the system is in a deliberately staged state: some pieces are live, some are tested, and some are still design work.

  • Ingestion and triage: the existing Grafana → Keep → Holmes flow remains enabled.
  • Prompt: a shortened prompt was loaded as workflow revision 31, with previous text archived.
  • Environment skill: the complete reference was restored after a Helm override regression.
  • Holmes wrapper: conflicting mandatory narration was removed, and CI plus rollout were verified.
  • Resolver safety: suppressed firing alerts are retained, and malformed responses fail closed.
  • Grouping: the existing alert name plus boundary grouping remains in place; no new dependency grouping has been deployed.
  • Closure: resolveOn: never plus a five-hour resolver remains.
  • Eligibility labels: prepared on a feature branch, but not deployed.
  • Admission and deduplication: core and read-only shadow adapter tested, but no live dispatcher or seeded ledger yet.
  • Answer quality: prompt-only comparison failed review; post-repair comparison is pending.

A useful mental model is this: a firing notification is not proof of delivery, incident creation, or a fresh investigation. It may simply join an existing incident. That distinction matters because many triage systems accidentally treat “alert fired” as “AI must investigate now.” This design deliberately avoids that shortcut.

What the evidence actually established

The strongest part of this work is that it does not assume a single root cause for poor AI answers. Instead, it separates regressions, prompt behavior, tooling constraints, and evidence gaps.

First, a GitOps change appended a partial skill overlay. Helm replaced the full content string, losing system locations, Loki selectors, and freshness guidance. That proves a regression, but it does not prove that every poor answer came from that regression. The distinction matters: a broken overlay can make answers worse, but it does not explain every missing log, unsupported causal claim, or weak diagnosis.

Second, the upstream Holmes wrapper required narration and checklists that conflicted with the workflow prompt. The custom image removes that exact block with a checksum guard. It does not replace tools or diagnostic skill content. In other words, the fix was about removing an unwanted constraint, not pretending the model suddenly had better diagnostic instincts.

Third, prompt revision 31 did not fix quality by itself. One execution completed in 812 seconds with 38 calls, but it still failed review because it missed subject logs and made an unsupported CPU causality claim. Cumulative usage was 865,006 tokens, including repeated and cached context, not one context window. Tool time summed to about 15.9 seconds, but the remaining time is not thereby proven to be purely model computation. That level of precision matters when you are trying to decide whether a prompt, tool, model, or evidence gap is the real problem.

Fourth, later low container CPU samples do not disprove earlier high CPU. The correct finding is not “CPU was fine,” but rather “the claimed cause and time window are missing evidence.” That is a much more useful conclusion for an AI triage system, because it keeps the investigation honest instead of forcing a tidy story.

Fifth, earlier GitLab investigations were useful. The project → branch → pipeline → failed job trace procedure should be preserved as a regression test. If a future change breaks that trace path, the system should notice.

The approved repair chain was: canonical source 8b0f401, scoped installer 7273fb5, Flux skill publication through e64e676, and wrapper deployment 7926f67. Pipeline 44560 passed, Helm became Ready, and the running image digest plus absence of forced narration were verified. Model and toolset hashes were unchanged. The exact evidence lives in k8s-mgmt-flux/docs/triage-experiments/prompt-v31-powerful-owl.yaml.

Ownership: who owns what

One of the biggest failure modes in homelab AI tooling is unclear ownership. If every repository can change prompts, skills, workflows, and runtime behavior, the system becomes a pile of overlapping assumptions. The design here assigns responsibility deliberately.

  • k8s-flux: production Grafana rules, labels, and eligibility validation.
  • k8s-mgmt-flux: Keep/Robusta GitOps, encrypted workflows, prompt archives, rendered skills, lifecycle code, and experiments.
  • dev-workspace-config: canonical harness-agnostic skills and scoped installation.
  • container-images: CI-built, digest-pinned Holmes derivative and build tests.
  • ai-setup / container-control: existing model runtime and control, held constant during comparisons.
  • docs-and-planning: cross-repository design, not duplicate deployment manifests.

Operational sources include k8s-mgmt-flux/docs/triage-operations-runbook.md, docs/holmes-prompt-design.md, docs/triage-admission-design.md, and docs/triage-resolver-validation.md. The image build guide lives in container-images/docs/holmes-skill-wrapper-build.md.

This ownership model is not bureaucratic. It is what makes the system debuggable. When an answer is bad, you need to know whether the problem came from alert identity, prompt behavior, skill content, wrapper constraints, model runtime, or missing evidence.

Target design: identity and eligibility

The target design separates three things that are often accidentally merged: stable source/rule/boundary identity, affected subjects, and display titles. That separation is the foundation for better triage.

Alerts should carry structured context rather than serializing a database into an incident name. Real cluster, namespace, service, and container labels should be preserved. Missing identity should be treated as explicit uncertainty, not as permission to pick the busiest host and hope for the best.

The prepared triage policy distinguishes investigate from observe-only, with a reason for known NAS capacity alerts. Name-specific CEL exclusions should be replaced only after migration validation. Opting out of AI does not hide the alert; different NAS symptoms can still justify investigation.

This is a small idea with a large payoff. If the system knows what an alert is, what it affects, and what it is allowed to do, then it can make better decisions about whether to investigate, join an existing incident, or simply observe.

Target design: lifecycle

Lifecycle is where triage systems either become calm or become noisy. The current correlation uses alert name plus boundary, a 12-hour window, and resolveOn: never, with cron jobs providing closure. Shortening closure alone can increase new incidents and repeated AI calls, so the proposed design is more careful.

The proposed persistent gate admits initial impact, material new impact, and verified recurrence. It coalesces pending work and requires continuous explicit recovery. Silence, missing data, and stale samples are not recovery. A running slot should not be freed on timeout; the real execution should be reconciled. Prior successful investigations should be seeded before enabling the gate. And the system should never run both automatic dispatch paths at the same time.

That last rule is especially important. If two dispatch paths can fire, the system can create duplicate incidents, duplicate AI calls, and duplicate “investigations” that are really the same evidence being interpreted twice. A calm triage system needs one authoritative path.

Target design: skills and dependencies

The universal prompt should remain concise: scope, evidence, and response rules. Skills should describe system locations, label semantics, safe tools, and helpful diagnostic procedures. They should not contain predetermined diagnoses. A skill per alert is not required.

The full environment reference should be preserved, and changes should be measured before replacing it. This is a practical homelab lesson: the most valuable skill is often the one that tells the model where to look, how to read labels, and which tools are safe to use. It is not the one that tells the model what the answer must be.

Application YAML should declare stable service IDs, ownership, hosting, evidence selectors, and explicit dependencies. The schema, location, freshness checks, and initial inventory still need to be designed and tested. DNS, NFS, and network causality require an actual link, not co-location or timing alone. Individual symptoms should remain visible.

This dependency-aware approach should run alongside the current correlation first. That is the safe way to prove it works: compare the new dependency view against the existing grouping before making it the primary source of truth.

Completion sequence

  1. Review one post-repair run, then historically good GitLab, Kubernetes, datasource, and recurring-incident cases. Record exact versions, evidence, time, tool errors, and tokens. Live reruns are not frozen-input A/B tests.
  2. Verify Grafana firing/resolved delivery into Keep, including silence, all-clear, late events, and incomplete reads. A provider annotation-history failure does not prove resolved push delivery cannot work.
  3. Finish history seeding, non-Grafana normalization, durable dispatch, ambiguous-request handling, backups, and health metrics for admission.
  4. Shadow-test label and identity migration, then cut over through GitOps. Prove initial triage, no short-flap repeats, and genuine recovery/recurrence.
  5. Implement the dependency inventory beside existing grouping. If needed, compare Pi/Holmes with equivalent model, settings, and evidence. Replacing the harness is not yet a proven requirement.
  6. Observe 24–48 hours after cutover and review missed or noisy cases. This is a proposed acceptance window, not completed evidence or a promised deadline.

The sequence is intentionally conservative. It favors evidence over enthusiasm. It asks the system to prove that it can handle the boring cases before it is allowed to claim that it can handle the interesting ones.

Verification and unmanaged state

From k8s-mgmt-flux, with Python 3, PyYAML, and the management kubeconfig, the verification commands are:

PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -v
python3 scripts/triage-provenance.py
python3 scripts/triage_execution_report.py <execution-id>

At rollout, 39 tests passed. Fixture success is not diagnosis quality, but it is a necessary guardrail. Versions include Keep app 0.54.3/chart 0.1.97, Robusta chart 0.47.0, and the Holmes derivative a83b7ae6, with the digest pinned in GitOps. Official sources are the Keep Helm charts, Robusta charts, and HolmesGPT.

Not in Git: plaintext credentials, private age keys, raw model conversations, live incident history, and future ledger/WAL/backups. Encrypted Secrets, canonical skills, prompt history, and reviewed experiment records are in Git.

Why this matters for a homelab

A homelab AI triage system is not just a toy. It is a control plane for understanding your own infrastructure. If it is noisy, it trains you to ignore it. If it is opaque, it becomes a black box you cannot trust. If it is honest about what it knows, what it does not know, and what evidence it used, it becomes a genuinely useful part of the stack.

The design in this post is not about making the AI sound smarter. It is about making the system more reliable: preserve the working path, fix the regressions, keep ownership clear, make identity explicit, make lifecycle safe, and let dependencies be declared rather than guessed. That is the kind of engineering that turns a clever experiment into something you can actually live with.
