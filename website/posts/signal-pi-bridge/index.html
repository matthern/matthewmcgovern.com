A Signal Bridge for My Coding Agent

A note-to-self on Signal becomes a work turn for a dedicated coding-agent session in my homelab — and the agent's reply comes back over Signal.

Matthew McGovern · September 26, 2026

A note-to-self I send from my phone on Signal becomes a work turn for a dedicated pi coding-agent session in my self-hosted homelab, and the agent's reply comes back over Signal. End-to-end verified with real phone cycles: replies in roughly two to five minutes, agent's full work included.

What it does

I send a note-to-self on Signal — "check why the deploy pipeline is failing" — and a few minutes later the agent's answer arrives in the same thread. The agent is a dedicated pi coding session on one of my homelab hosts. The pipeline: phone → Signal sync protocol → a signal-cli daemon (a linked device) in a Docker container → WebSocket → a zero-dependency Node bridge (systemd user service) → herdr, the session manager hosting my agent sessions → pi → reply extracted from the session transcript → back over Signal.

Why I built it

The outbound half already existed: since July 2026 any of my agents could message me on Signal. What was missing was inbound — my phone as a control plane. My agent sessions are long-lived and stateful; I wanted to hand a task to the right session from anywhere, without touching a keyboard, and get the result where I already look. The hard part turned out to be Signal's device model, not the agent side.

How it works

The daemon is a linked device, not a second account

The homelab host is a linked (secondary) device of my phone's account. That one fact explains most of the design: my notes-to-self don't arrive as ordinary incoming messages — they arrive as sync messages the primary phone pushes to its linked devices. And since there is no second account or number, nothing external can point at the box: the bridge triggers only on notes-to-self from the primary device (my number, device 1, non-empty body) and logs-and-drops everything else.

Getting the device linked: two upstream bugs

Linking the host as a second device was a debugging saga, and it wasn't my setup — it was two independent upstream signal-cli bugs, each with evidence:

  • The 0.14.5-era link socket died at ~60 seconds: a Signal server-side infrastructure change in June 2026 (AsamK/signal-cli#2074). Fixed by moving to an image bundling signal-cli 0.14.7 — verified the socket survives past the 60s mark where it previously died.
  • With the socket fixed, every scan still failed with "invalid response": the link URI was missing &capabilities=nopni (AsamK/signal-cli#2123), required for linked devices with no phone number of their own — exactly this case. The upstream fix existed as a commit but not in any released image, so my QR script fetches the raw URI and appends the parameter client-side.

Real phone scan in September 2026: linked, verified both directions.

The envelope contract (the hard-won part)

Three shapes arrive on the WebSocket, and getting them wrong drops messages silently. A regular incoming message carries text under dataMessage; a note-to-self from the primary phone carries no dataMessage at all — it arrives as syncMessage.sentMessage; and text past the inline limit arrives as a text/x-signal-plain attachment, fetched by ID and appended. The first E2E bug: my bridge only looked at dataMessage, so every phone note was dropped as "no text — ignored"; the ignore-log line was the only trace. The fix is the unwrap:

const inner = env.dataMessage ?? env.syncMessage?.sentMessage;

Deduplication has a twist: modern signal-cli no longer exposes a GUID on envelopes, so the key is source + timestamp + SHA-1(body), persisted in a bounded state file — network replays and restarts can't double-drive the agent, and losing the file costs at worst one duplicate.

Agent status semantics (the second E2E bug)

The bridge waits for the session to be ready before injecting, and the status vocabulary bit me: a fresh session reports idle, but a finished turn reports done — not idle. My first version waited on idle alone, so a completed turn hung until the turn timeout and produced a false "couldn't extract a reply". Both idle and done mean "ready for a new turn". Reply extraction is content-based, not status-based: the last assistant message at or after the injection timestamp, read from the session transcript — which is what makes a short grace window for the transcript's flush race safe.

Rounding out the design: push over polling (the daemon pushes every envelope; the bridge probes and reconnects with backoff); one serialized queue, one turn in flight; timeouts that message the phone instead of the void; and auto-spawn of a missing session through my standard pi launcher.

Results

End-to-end verified in September 2026 with three real phone note-to-self cycles: replies delivered back over Signal in ~105s, ~147s and ~305s, each including the agent's full turn. Both bugs above were found and fixed during that pass — neither shows up in unit-level testing; both are artifacts of the real phone → server → daemon path. The bridge itself is a ~350-line, zero-dependency Node script plus a systemd unit.

What I learned, and what's next

  • A linked device sees different envelope shapes than a registered primary. You learn that from one dropped message and an "ignored" log line, not from documentation. E2E with a real phone is the test.
  • Verify which side is actually broken. "Invalid response" during linking looked like my bug; the daemon log showed the rejection coming from Signal's servers.
  • Known limitation, documented: envelopes live in daemon memory only, so notes sent while the container is down are lost. Next: a durable queue, and non-text attachments (images) for a v2 trigger.
