An AI Blog Writer That Does Its Research

My blog's drafts are now written by a coding agent that reads the actual docs and git history first — each post ships as a merge request with a local preview, a redaction gate, and a revision loop.

Matthew McGovern · September 27, 2026

My blog's drafts are now written by a coding agent that reads the actual docs and git history first — each post ships as a merge request with a local preview, a redaction gate, and a revision loop.

What it does

I keep a technical blog and an internal design doc behind every build. The blog-automation repo closes the loop between them: a Python trigger script picks a topic — a design doc, or a repo I name — and hands it to a coding agent (pi) running a blog-post-writer skill. The agent researches the doc, its repo, and the git history; writes a short first-person post; strips anything identifying my infrastructure; splices it into the site template; and opens a merge request with a local preview. I get a push with the MR and preview links, review the rendered post, reply with @ai [feedback], and the agent revises in place — merging deploys.

Why I built it

Version one called a local LLM server directly: one prompt, no tools, no context. The model wrote the whole post from memory of the topic name — generic, and confidently wrong about specifics. It also kept hitting mechanical failures: CLI version drift, drifted template markers, a dead deploy flag. The fix wasn't a better prompt — it was giving the writer the source doc, the code, and the commit history. In late September 2026 I rebuilt the bot around an agent loop with tools; the script became a thin trigger: topic selection, GitLab plumbing, forwarding.

How it works

A thin trigger, an agent that does the work

Two modes. Draft picks a topic — an explicit target (doc path, repo name, or free text) or a random unpublished design doc; a cache file records what's posted, a hold file skips WIP docs. It then starts a non-interactive agent session with the skill: research, write, redact, package. Revise scans open auto-blog merge requests for @ai feedback and runs a fresh agent session per MR, rewriting the body in place. The bot's MR replies start with a robot emoji, and that marker is the dedup: a reply newer than the newest feedback note means the MR is skipped — the fifteen-minute schedule is a cheap no-op.

# a bot reply newer than the newest @ai note = already handled (notes newest-first)

The agent runs where the material lives

Drafts must be written on the machine hosting my checkouts — docs, website repo, the skill. The trigger can run elsewhere (CI container, systemd timer), so when the agent isn't local the script forwards the invocation over SSH as the homelab user — CI jobs run as root, and the key belongs to the regular user. Two environment bugs cost real time here:

  • The forwarding SSH key had to load into an ssh-agent before the job script ran; the first attempt loaded it in the post-job hook — too late.
  • My Node toolchain is managed by nvm, which only loads in interactive shells; non-interactive sessions had no pi on PATH until I prepended the install's bin directory.

Merge requests as the review surface

Every post is a merge request, not a deploy. The agent splices the body into the site's HTML template, creates an auto-blog-YYYY-MM-DD-<slug> branch off main, pushes, opens the MR, rsyncs the site to the preview server, verifies the preview returns 200, then sends the push notification. A single-MR policy keeps merges clean: the bot refuses to draft while an auto-blog MR is open, and drafts always base on main — no stacking, no posts-index conflicts. One quirk shaped the wiring: this GitLab version silently drops scheduled-pipeline variables via the API, so the CI rules key off pipeline source instead.

A redaction gate, not an afterthought

My source docs are full of internal hostnames, IP ranges, and service names. Redaction is part of the skill's contract: before packaging, the body is grepped against a pattern list of identifying strings, and any hit means fix-and-retry. It's also why the bot repo and skill live in a private repository — their prompts and paths are themselves identifying. The local preview is where I check the actual rendering — it caught a first-version bug where template replacement targeted markers that no longer existed, shipping a draft with placeholder text in the browser tab. The splice script now targets the real markers, and the preview makes that failure class visible before merge.

How it performs

  • End-to-end verified on the first two posts: a full draft (~850 words) and the revise loop, run twice on one MR — once from a CI container, over SSH, completing a revision, commit, MR reply, and preview sync.
  • One agent session — research, write, redaction, package — takes about 7–10 minutes.
  • Revise runs on a fifteen-minute GitLab schedule; draft runs on a weekly local timer, currently paused while I sign off drafts by hand.
  • The trigger script is ~330 lines; the writing is the skill's prompt plus the agent's tool use.

What I learned, and what's next

  • One prompt to a local LLM versus an agent with the actual repo and git history: generic filler versus a post with real commit references. Tools beat prompts.
  • Make the review surface a merge request: redaction review, tone feedback, and the deploy gate live in one place, and a human stays the merge button.

Next: re-enable the weekly draft timer once drafts are signed off, and point the picker at plans and runbooks — the most identifying sources, redacted harder.
