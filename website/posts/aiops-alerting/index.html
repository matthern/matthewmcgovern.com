Wiring AI Alert Triage Across Two Kubernetes Clusters

Keep correlates Grafana and Zabbix alerts into incidents and a local LLM investigates each one, while Pushover still pages me directly. The hard part was the label contract between three systems, not the model.

Matthew McGovern · September 27, 2026

Keep correlates Grafana and Zabbix alerts into incidents and a local LLM investigates each one, while Pushover still pages me directly. The hard part was the label contract between three systems, not the model.

What it does

Every alert the homelab raises ends up as an incident with a written root-cause analysis: alerts produced on a production Kubernetes cluster (Grafana plus Zabbix) are consumed on a separate management cluster by Keep, which correlates them into incidents and hands each new one to HolmesGPT — a local 27B-parameter Qwen model on llama.cpp with read-only access to both clusters.

The AI layer is additive: humans get Pushover straight from the producers, so a failure in the AI path never causes a missed page.

Why I built it

The estate spans two clusters and a dozen bare-metal hosts behind two alert systems, and "something is broken" was always the cheap part of an incident. The expensive part was the investigation — which failure domain, one fault or several, what the causal chain is. I wanted that automated, with one hard constraint: the AI never sits between an alert and the pager.

How it works

A label contract, not a convention

Grouping is applied three times by systems that share no definition: PromQL decides which labels survive aggregation, Grafana which alerts become one notification, Keep which become one incident. Any layer grouping on a narrower key set silently undoes everything above it.

Keep's correlation fingerprint fails closed: a missing grouping label does not fall back to a narrower grouping — it collapses into one shared bucket with every other incomplete alert. Adding instance merged all my Kubernetes alerts into one incident; adding namespace merged everything — fifteen unrelated alerts became one. Coverage over 175 real alerts: alertname 175/175, instance 89/175, namespace 65/175.

So the label set became a contract enforced in CI: an audit of the 37 rules found 13 identity shapes and no label common to all, so every rule emits two labels built into the query — target, the subject that names the incident, and boundary, the failure domain: the single thing breaking that would account for every alert in it. Where a shared dependency fails across many subjects — backups, a certificate authority — the rules name the subsystem instead, so one fault is one incident, not one investigation per subject.

The incident lifecycle

Three systems hold an opinion about whether something is still broken, and they do not talk back to each other. Grafana is the only source of truth for alert state; Keep holds incidents — groupings of notifications — and nothing done to one changes whether the alert is firing. There is a fourth state that surprises people: expired, which never appears in the UI; it decides whether a new alert reuses an existing incident or creates one.

Resolving everything in Keep does nothing: the alerts still fire, the next repeat finds the resolved — therefore expired — incident, creates a new one, and incident creation is the AI trigger. Manual resolution is worse than cosmetic — it guarantees a fresh round of investigations. To stop an alert, fix the condition or silence it upstream.

Closure is owned by one scheduled job that closes an incident only when every linked alert has stayed resolved for a fixed delay. And the correlation window must sit below the notification repeat interval: at the original one hour against a 24-hour repeat, every reminder created a new incident — eight open incidents for one ongoing fault; widen it past the repeat and a still-broken condition stops producing creation events entirely, investigated once, then silent. Twelve hours against a 24-hour repeat is the working point: a daily re-look, with the previous conclusion carried forward so the repeat confirms or revises instead of restarting.

The failure that proved the design

Eight containers were restarting across both clusters. Notification grouping omitted cluster, so they arrived as one notification and correlated into one incident. The model reasoned correctly over that merged input and produced a confident story: a memory leak on a management-cluster node, with a production database listed as collateral damage. A node exhausting memory on one cluster cannot restart a pod on another; the production database's fault was unrelated and six weeks old. The merge gave a real failure a plausible, confident, wrong explanation — the kind nobody re-opens.

The model was not at fault. The defect was one layer upstream, in the label contract.

Results

  • 37 Grafana rules in 17 groups, every one label-validated in CI; Zabbix from both clusters feeds the same pipeline.
  • A flapping media-server container that produced ten investigations in three hours now produces one, investigated once.
  • A single ongoing fault that produced eight open incidents in 26 hours now produces one per day, each confirming the previous analysis.
  • Every incident arrives with a written root-cause analysis — and every alert still pages me directly.

What I learned, and what's next

Every interesting failure — merged incidents, duplicate investigations, triage going silent — was a grouping or lifecycle problem one layer upstream. The sharp edges are real: the incident lookup is check-then-act with no lock, so alerts in the same second can still duplicate (three incidents, one second apart), and upstream dedup is blocked on a provider bug.

Next: topology mapping so incidents carry their service dependencies, explainable correlation, and a serialized re-triage runtime moving to live dispatch.
