Wiring AI Alert Triage Across My Whole Homelab

Every alert the homelab raises — two Kubernetes clusters, the VMs, the docker hosts, the storage — gets correlated into an incident by Keep and investigated by a local LLM. Pushover still pages me directly.

Matthew McGovern · September 27, 2026

What it does

Every alert my homelab raises ends up as an incident with a written root-cause analysis. Grafana rules watch the two Kubernetes clusters; Zabbix watches the rest of the estate — the Proxmox nodes and their VMs, the docker hosts, the storage. All of it lands in Keep, which correlates the alerts into incidents and hands each new one to HolmesGPT, backed by a local 27B Qwen model on llama.cpp with read-only access to both clusters and the monitoring APIs.

I still get paged directly by Pushover, straight from the producers. The AI layer is additive: it can explain an incident, but it can't sit between an alert and my phone.

Why I built it

The estate is too big to triage by hand, and "something is broken" is the cheap part of an incident. The expensive part is the investigation: which failure domain, one fault or several, what the causal chain is. I wanted that automated, with one hard constraint — the AI never sits in the paging path.

How it works

A label contract, not a convention

Grouping is applied three times by systems that share no definition: PromQL decides which labels survive aggregation, Grafana which alerts become one notification, Keep which become one incident. Any layer grouping on a narrower key set silently undoes everything above it.

Keep's correlation fingerprint fails closed: an alert missing a grouping label does not fall back to a narrower grouping — it collapses into one shared bucket with every other incomplete alert. Coverage over 175 real alerts: alertname 175/175, instance 89/175, namespace 65/175. Adding instance merged all my Kubernetes alerts into one incident; adding namespace merged everything — fifteen unrelated alerts became one.

So the label set became a contract enforced in CI. An audit of the 37 rules found 13 identity shapes and no label common to all, so every rule builds two labels into its query: target, the subject that names the incident, and boundary, the failure domain — the single thing whose failure would account for every alert in it. Where a shared dependency fails across many subjects — backups, a certificate authority — the rules name the subsystem instead: one fault, one incident.

The incident lifecycle

Grafana is the only source of truth for alert state; Keep holds incidents — groupings of notifications — and nothing done to one changes whether the alert is firing. The state that surprises people is expired: it never appears in the UI. It decides whether a new alert reuses an incident or creates one — and incident creation is the AI trigger.

Resolving everything in Keep does nothing: the alerts still fire, the next repeat finds the resolved — therefore expired — incident, creates a new one, and guarantees a fresh round of investigations. To stop an alert, fix the condition or silence it upstream. Closure is owned by one scheduled job that closes an incident only when every linked alert has stayed resolved for a fixed delay.

The correlation window has to be tuned against the notification repeat interval. At the original one hour against a 24-hour repeat, every reminder created a new incident — eight open incidents for one ongoing backup fault, each re-investigated. Widening past the repeat meant a persisting fault was investigated once, ever, and then Keep went quiet about it. The working point is twelve hours against the 24-hour repeat: a daily re-look, with the previous conclusion carried forward so each repeat confirms or revises instead of starting cold.

The failure that proved the design

Eight containers were restarting across both clusters. Notification grouping omitted the cluster, so they arrived as one notification and correlated into one incident. The model reasoned correctly over that merged input and produced a confident story: a memory leak on a management-cluster node, with a production database listed as collateral damage. A node exhausting memory on one cluster cannot restart a pod on another; the database's fault was unrelated and six weeks old. The merge gave a real failure a plausible, confident, wrong explanation.

The model was not at fault. The defect was one layer upstream, in the label contract.

Results

  • 37 Grafana rules in 17 groups, every one label-validated in CI; both Zabbix servers feed the same pipeline.
  • A flapping media-server container produced ten investigations in three hours; now it produces one.
  • A single ongoing fault that produced eight open incidents now produces one per day, each confirming the previous analysis.
  • Every incident arrives with a written root-cause analysis — and every alert still pages me directly.

What I learned, and what's next

Every interesting failure — merged incidents, duplicate investigations, triage going silent — was a grouping or lifecycle problem one layer upstream. The sharp edges are real: the incident lookup is check-then-act with no lock, so alerts in the same second can still duplicate (three incidents, one second apart), and upstream dedup is blocked on a provider bug.

Next: topology mapping so incidents carry their service dependencies, explainable correlation, and hardening the serialized re-triage runtime that just moved to live dispatch.
